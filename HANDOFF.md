## Sequence 5 — completed
- Migration `0003_active_run_pointer`: adds `questions.active_run_id` (nullable FK → `coding_runs.id`, `ON DELETE SET NULL`) — pure bookkeeping, moved by `reset` and auto-advanced whenever any run finishes `apply`. Required a `foreign_keys=` disambiguation on **both** `CodingRun.question` and `Question.coding_runs` once a second FK path existed between the two tables (SQLAlchemy can't infer which FK a plain `relationship()` should join on when there's more than one) — see the bug note below.
- `POST /api/runs/{id}/split` `{parent_code_id, subcodes?, subcode_definitions?, n_proposed?, preserve_parent?, enrich_subcodes?}` — single-parent shorthand — **or** `{parent_codes: [{parent_code_id, subcodes?, ...}, ...]}` for the "multi-config splits create one child run each" case: split several *different* parent codes in one request, each into its own independent child run (confirmed with the user — the alternative reading, trying several sub-code configs of the *same* parent code, was rejected). `POST /api/runs/{id}/merge` `{code_ids, merged_name?, merged_code_id?, merged_definition?, enrich_merged?}` (`app/routers/refine.py`) — parent must be `APPLIED` (409 otherwise). Each creates a `DRAFT` child `CodingRun` (`kind=SPLIT`/`MERGE`, `parent_run_id` set) and enqueues `app/jobs/refine.py`, which:
  1. Reconstructs the parent's coded dataframe from its `CodeAssignment` rows (`app/jobs/refine_common.py::build_coded_dataframe` — Sequence 4 never kept the intermediate pandas frame, only the final assignments, so this pivots them back into the `code_<name>`/`conf_<name>` shape `codeframe.coding`/`refine`/`reporting` all expect).
  2. Calls `codeframe.refine.split_code`/`merge_codes` (Sequence 1, unmodified) **once**, which both proposes the new code(s) *and* recodes the affected rows in the same call.
  3. Flattens the full resulting dataframe (inherited codes + new ones, every response) into `config_json["staged_assignments"]`, and marks only the *new* code(s) `"proposed"` — inherited/untouched codes are carried over already `"accepted"` (no need to re-review something nobody touched).
  - Review/finalize reuse Sequence 4's endpoints **unchanged** — a split/merge child is just a `CodingRun` like any other at that point.
  - `POST /api/runs/{id}/apply` (`app/jobs/apply.py`, extended) now branches on `run.kind`: `S2`/`S3` runs code from scratch as before; `SPLIT`/`MERGE` runs materialize `staged_assignments` filtered to whatever's still `"accepted"` after review — no LLM calls happen at apply time for these, since `split_code`/`merge_codes` already did the recoding at *propose* time. **Merge frequency is a true set union**: `merge_codes` computes the merged code column as `df[source_cols].max(axis=1)` (logical OR across source columns), not a sum — verified with a genuinely overlapping (multi-label) row forced in via direct DB insert, since the fake LLM never produces multi-label output on its own (`tests/refine/test_merge.py::test_merge_frequency_is_union_not_sum`).
  - Every successful apply (any kind) now sets `question.active_run_id = run.id` — "most recent apply wins" until someone resets.
- `POST /api/questions/{id}/reset?to_run={run_id}` — validates `to_run` belongs to the question and is `APPLIED` (404/409 otherwise), then just moves `active_run_id`. **Nothing is ever deleted**; a later branch stays fully `APPLIED` and queryable after reset, and splitting again from the reset target creates an independent sibling branch (`tests/refine/test_reset.py`).
- Results (`app/routers/results.py`, run must be `APPLIED`, all via `build_coded_dataframe`): `GET /results/frequencies` and `/cooccurrence` wrap `codeframe.reporting`'s existing `frequency_table`/`cooccurrence_matrix` (Sequence 1) directly — no new counting logic. `GET /results/codebook` returns accepted codes as-is. `GET /responses?search=&code=&page=&page_size=` paginates the same dataframe (`page_size` capped at 200).
- Exports (`app/jobs/exports.py` + `app/routers/results.py`): `POST /runs/{id}/exports?format=xlsx|csv_frequencies|csv_coded|png_frequencies|png_cooccurrence` enqueues a job that renders via `codeframe.reporting.export_workbook`/`frequency_table`/`export_charts` (all Sequence 1, unmodified), uploads to MinIO, and writes an `ExportArtifact` row (modeled in Sequence 2, unused until now). `GET /api/jobs/{id}` now also returns `"result"` (the job's return value, via `job.return_value()` — RQ deprecated the old `.result` property) once `status == "finished"`, so the caller learns the new `artifact_id` without a separate endpoint. `GET /api/exports/{id}` returns a presigned MinIO URL (`storage.presign_url`, from Sequence 2).
- `tests/refine/` + `tests/exports/` (27 tests total): `test_split.py`, `test_merge.py` (union-not-sum, verified against a forced real overlap), `test_reset.py` (branch-without-disturbing-original), `test_exports.py` (5-sheet workbook, PNG magic-byte checks, presigned-URL downloads via `httpx`), `test_results_api.py` (pagination/search/filter math on a 200-row fixture). Both suites share a `build_applied_run` conftest fixture that walks import→accept→finalize→apply once, on top of Sequence 4's direct-DB-insert `seed_dataset` pattern.
- `scripts/manual_refine_flow.sh` (new): the fullest manual walkthrough yet — upload→preprocess→**AI** codebook (not import, unlike the automated tests) →review→finalize→apply→**split with subcodes omitted** (exercises `codeframe.refine.split_code`'s AI-proposal branch, which no automated test in this repo reaches through the full API) →review→finalize→apply→**merge with merged_name omitted** (same, for `merge_codes`'s AI-naming branch) →review→finalize→apply→reset→confirm the split branch is untouched→export xlsx (downloads via presigned URL, confirms exactly 5 sheets with `openpyxl`)→export PNG (confirms magic bytes). Run via a throwaway `python:3.11-slim` container on `codebench_default` per the Sequence 4 lesson (this host's stray port-8000 process is apparently still there).
- One implementation bug found and fixed **before** it reached tests: adding `questions.active_run_id` (a second FK between `questions` and `coding_runs`) broke `CodingRun.question`'s existing `relationship()` — SQLAlchemy raised `InvalidRequestError: ... multiple foreign key paths` at mapper-configure time, surfaced as a 500 on the very first API call in every test. Fixed by adding `foreign_keys=[question_id]` to `CodingRun.question` (in addition to the `foreign_keys="CodingRun.question_id"` already added on `Question.coding_runs`) — **both sides** of an ambiguous relationship need disambiguating, not just the one that "looks" ambiguous.
- **Design call flagged and corrected mid-session:** first implementation read "multi-config splits create one child run each" as trying several sub-code configurations of the *same* parent code (`configs: [...]` alongside a single `parent_code_id`). User clarified the intended meaning is the other reading — split several *different* parent codes in one request, each into its own child run. Reworked to `parent_codes: [{parent_code_id, subcodes?, ...}, ...]` (each child only touches its own parent code; the other parent codes are carried over untouched in every child, since all children branch off the same original parent run) — see `app/routers/refine.py::SplitRequest`/`ParentSplitConfig` and `tests/refine/test_split.py`.

## Note for next session
- `make.exe` is still blocked on this Windows host by an Application Control policy — use raw `docker compose` commands locally.
- **Always run `docker compose build` (all services, no service arg) after backend code changes** — `api` and `worker` are separate images from the same Dockerfile and silently drift apart otherwise. This bit us again this session (had to rebuild after the FK-disambiguation fix) — third time this has happened across sequences; treat it as inherent to this project's setup, not a one-off to eventually stop checking for.
- **Always run `docker compose run --rm api ruff check .` AND `bash scripts/check_org_scoping.sh` locally before opening a PR**, in addition to `pytest`.
- This host has an unrelated stray Python process bound to `127.0.0.1:8000` from a different, unrelated project (`codeframe-webapp`) that intercepts plain `curl http://localhost:8000/...`. Don't kill it without asking; instead run manual flows via `docker run --rm --network codebench_default ...` hitting `http://api:8000` (Docker service DNS), as both Sequence 4 and 5's manual scripts did.
- When building a job that mutates a JSONB column in place, remember `sqlalchemy.orm.attributes.flag_modified(obj, "column_name")`.
- **Adding a second FK between two tables that already have a `relationship()` between them requires `foreign_keys=` on *both* sides of the existing relationship, not just the new one** — this session's bug. Check this proactively any time a new FK is added to a model that already has a `relationship()` pointing at the same target table.
- Idempotency (delete-then-insert before writing job output) is now standing practice for every job that writes DB rows — Sequence 5's split/merge apply path inherited this for free by reusing `run_apply_job`'s existing delete-then-insert, and the manual flow's reset+re-branch step is the lineage equivalent (nothing ever deleted, safe to redo).
